# 路线图

这份文档记录 Finallyshell（finallyshell 的 `dev` 分支）已经做了什么、正在做什么、接下来做什么，以及每项功能的范围和约束。新增想法时追加到对应的段落；某项开工时移到“进行中”，发布后移到“已发布”并写上版本号。

功能的具体行为写在 [features.md](features.md)，设置项和文件写在 [configuration.md](configuration.md)，代码结构写在 [development.md](development.md)。本文只讲规划。

## 定位和原则

- **SSH 客户端为主，客户端版的服务器面板为辅。** 参照 FinalShell、Xshell、MobaXterm、Termius、WindTerm 的终端和文件体验，再把宝塔、1Panel、DPanel、Portainer 里最常用的服务器管理功能搬进客户端。不在服务器上装任何东西，全部通过 SSH 完成。
- **每项只做最常用的八成。** 不追求功能大全；用得少、维护成本高的部分不做或往后放。
- **生产安全优先。** 用户的服务器都是生产环境：
  - 删除、清理、重建、重启服务、改防火墙、改系统配置等修改操作，执行前一律确认，写清楚会动什么、后果是什么。能撤销的提供撤销，能备份的先备份。
  - 测试一律用模拟后端（可注入的命令执行器、内存里的假服务），绝不在真实服务器上跑修改命令。
  - 拼命令时每个参数都加单引号，名称和 ID 先校验，不把用户输入直接拼进 shell。
- **需要 root 的操作统一走提权。** 顺序见[提权](#提权)：能自动提权就自动，实在提不上去才提示，并告诉用户怎么开通权限。
- **密码和密钥不落地。** 只经加密的 SSH 通道写给 sudo、su 或 `--password-stdin`，不出现在命令行、进程列表、日志、输出窗口和截图里。要记住的存进系统凭据库。
- **两种语言同步。** 界面文案同时写 `locales/en.json` 和 `locales/zh-Hans.json`；文档同时改 `docs/en/` 和 `docs/zh-CN/`，标题和顺序保持一致。

## 不做

- 用户和权限管理：客户端只给自己用。
- 应用商店、一键建站：维护成本高，和 SSH 客户端的定位偏离太远。
- 在服务器上安装常驻程序：所有功能都只通过 SSH 完成。
- Mosh：Go 没有 Mosh 客户端库，要从头实现它的 UDP 状态同步协议和加密，风险高、收益有限；需要弱网体验时用 SSH 保活和自动重连代替。

## 开发方式

- **并发开发**：主会话负责调研、拆分、审查、合并和发布；每个模块交给一个 Codex CLI（GPT-6.2 Sol），各自在独立的 Git 工作树和分支里开发。任务说明放在仓库外。
- **避免冲突**：开工前先由主会话搭好骨架（标签、入口、每个模块一个占位文件），每个 Codex 只改自己的文件；文案键用各自的前缀，并插在两种语言文件里各自指定的锚点之后。
- **审查**：合并前逐个检查代码、命令边界、确认弹框、测试和截图（浅色、深色、中英文、宽窄两种尺寸）；修改类命令只认模拟测试的结果。
- **发布**：合并进 `dev` 并推送后，GitHub 先跑完整测试（`go test -race ./...`），再打包各平台并发布 `v2.0.N`；macOS 打包机器排不上队时，其他平台照常发布。
